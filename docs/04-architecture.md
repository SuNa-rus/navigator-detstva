# Предварительная архитектура системы

## 1. Назначение

Документ описывает предварительную архитектуру платформы «Навигатор детства». Архитектура является концептуальной и должна быть уточнена после согласования требований с заказчиком.

## 2. Общая структура

Предлагается построить систему по клиент-серверной модели.

Основные компоненты:

1. **Клиентский интерфейс** — веб-интерфейс для родителей, медицинских работников, редакторов и администраторов.
2. **Сервер приложения** — обработка запросов, реализация бизнес-правил и проверка прав доступа.
3. **База данных** — хранение образовательных материалов, категорий, сведений о маршрутах и учётных записей, если они предусмотрены.
4. **Модуль управления контентом** — создание, редактирование, проверка и публикация материалов.
5. **Модуль цифрового маршрута** — отображение этапов и связанных с ними информационных материалов.
6. **Модуль авторизации и контроля доступа** — проверка пользователя и предоставленных ему полномочий, если авторизация входит в согласованный объём.

## 3. Логическая схема

Пользователь взаимодействует с клиентским интерфейсом. Интерфейс отправляет запросы серверу приложения. Сервер проверяет запросы и права доступа, обращается к базе данных и возвращает результат клиенту.

Модули управления контентом и цифрового маршрута используют общую серверную логику и данные. Доступ к административным функциям ограничивается соответствующими ролями.

## 4. Предлагаемые технологические решения

На этапе анализа окончательный технологический стек не утверждён.

В качестве одного из вариантов можно рассмотреть:

- **Frontend:** HTML, CSS и JavaScript либо современный frontend-фреймворк.
- **Backend:** серверное приложение на одном из распространённых языков программирования.
- **База данных:** реляционная СУБД, например PostgreSQL.
- **Контроль версий:** Git и GitHub.
- **Документация и диаграммы:** Markdown и Excalidraw.

Выбор конкретных технологий должен учитывать компетенции команды, требования заказчика, инфраструктуру медицинской организации и сроки проекта.

## 5. Безопасность

Архитектура должна предусматривать:

- разграничение доступа в соответствии с ролями пользователей;
- защищённую передачу данных;
- безопасное хранение учётных данных;
- проверку входных данных;
- регистрацию значимых событий безопасности, если это требуется;
- резервное копирование и восстановление данных;
- минимизацию объёма собираемых персональных данных.

Реальные медицинские сведения нельзя помещать в публичный репозиторий. Необходимость хранения таких сведений и допустимые способы интеграции должны быть согласованы с заказчиком.

## 6. Интеграции

Возможность интеграции с информационными системами больницы пока не подтверждена.

До проектирования интеграции необходимо выяснить:

- какие информационные системы используются;
- существует ли документированный API;
- какие данные разрешено передавать;
- кто отвечает за предоставление доступа;
- какие требования предъявляются к безопасности и журналированию.

Если интеграция не входит в первую версию, платформа должна работать в пределах самостоятельно согласованного набора функций.

Структура может изменяться по мере разработки. В папке `docs/diagrams/` планируется хранить архитектурные схемы в формате Excalidraw.

## 8. Основные риски

- Недостаточно уточнённые требования заказчика.
- Неизвестные ограничения действующих информационных систем.
- Требования к защите персональных и медицинских данных.
- Ограниченные сроки разработки.
- Возможность изменения технологического стека после технического обсуждения.

## 9. Следующие шаги

1. Обсудить предварительную архитектуру с командой и заказчиком.
2. Уточнить функциональность первой версии.
3. Выбрать технологический стек.
4. Подготовить диаграмму компонентов и потоков взаимодействия.
5. Согласовать требования к хранению данных и безопасности.
6. Зафиксировать окончательные архитектурные решения после обсуждения.
